# Bug hunt, first pass, 2026-10-11

The first pass of the plan in [../finding-bugs.md](../finding-bugs.md). It
covers what Peel believes at its boundaries, read against the code on both
sides, and the project's bug history so far, classified (the appendix).

Base: `origin/main` at `79b0fe0` (#164). Core paths are in
`~/Documents/sphinx`:
- at `bd9e140`, the rev Peel links;
- at `caa76a1`, the rev the local stack runs.

Mixer paths are at `caa76a1`.

Method:

- **History.** I read every PR, every commit on `main`, the open `fix/*`
  branches, the review docs and the phase journals. I classified each of
  the 205 bugs found so far by who found it, where it lived and how bad it
  was.
- **Boundaries.** I traced money, accounts and restore, the engine and
  sync, and the UI against the core, the mixer and the official Mac app.
- **Checks.** Each finding marked *verified* was read on both sides by
  hand before this was written.
- **Not done.** Nothing was run against a server, and no code was
  changed. The offline suite passed when I ran it: 551 tests, on #160's
  branch. #161 and #164 have since made it 544.

Labels, as in the payments review:

- **Severity:** *sats or account lost*, *messages lost*, *wrong state
  shown*, or *cosmetic*.
- **Confidence:** *verified* means read in the code on both sides; the
  table says where it is less than that.
- **Fix size:** S (an afternoon), M (a day or two), L (more, or outside
  Peel).

### N1. The core is 70 commits behind, and seven of them are client security fixes

Peel links `stakwork/sphinx` at `bd9e140` (v0.6.27, 2026-09-21). The route:

- `sphinx-rs` `f1e2d6c` pins that rev;
- Peel takes the Mac app's own static library
  (`scripts/build-ffi.sh:14`, checked against `Vendor/sphinxrs.lock`).

On 2026-09-25 upstream merged a security pass, labelled critical and
high. Eight of its commits change the core crate (`sphinx/src`). Seven of
those change what a client does, and none of them is in our build:

- **SR-016, two commits.**
  - A received amount is checked against the HTLC (the payments review's
    F3).
  - There is no automatic 3-sat answer to an unpaid key exchange (F2 in
    the keys and money audit, Audit A).
- **SR-017.** A contact record (type 33) is honoured only when this
  account sent it.
  - Ours takes one from anyone who can message the account, on the live
    path: `handle_msg.rs`, `MsgType::ContactKeyRecord`, at `bd9e140`.
  - `overwrite_incoming_type_33` then writes the record's route and
    contact key over the contact it names.
  - `Engine.swift:1078` and `AGENTS.md:515` say the core already refuses
    these. Peel has no check of its own.
- **SR-018 to SR-020.** Three panics a malformed message can trigger:
  - a contact-info length check that never ran;
  - a short payload in `decrypt`;
  - a short key in `check_if_pk`.

  The bindings turn a panic into a thrown error, so the message should be
  dropped rather than the app crashing.
- **SR-022.** The randomness behind tags, preimages, onion keys and child
  indexes came from the time and the seed alone.

The eighth, SR-021, is a panic only the mixer reaches.

No journey sends a forged record or a malformed field, so none could have
shown any of this.

The official apps ship the same core. `sphinx-rs` on GitHub still pins
`bd9e140` today, and its last push was 2026-09-23.

Fix:

- **The core.** No library with the fixes exists yet. `sphinx-rs` has to
  move its pin to v0.6.29 or later, and a library has to be built from it.
  The Sphinx team can do that for every app, or we can, which settles
  PLAN.md's open question about building from source.
- **Meanwhile, in Peel.** Refuse a live type 33 that would rewrite a
  contact who is already ready, with a unit test that feeds a made-up
  core reply.
- **The build.** Make `scripts/build-ffi.sh` refuse a library whose rev
  lacks a listed set of upstream commits (`git merge-base
  --is-ancestor`).
- **The comments.** Correct the two that describe the check.

### N2. A signup can delete the words of a funded account

How it happens:

1. `Account.signup` connects with the invite. If that throws, it deletes
   the profile unless the engine is registered (`Account.swift:52-58`).
   The words go with it (`Profile.delete`, `Profile.swift:76-81`).
2. `isRegistered` reads only local state (`Engine+Account.swift:53-55`).
3. `connect` throws if the server's reply has not landed within 30
   seconds (`Engine.swift:200-207`, `:307-311`).
4. The mixer redeems the invite and credits the new account before it
   replies (`mixer/src/routes.rs`, `register`: `redeem_initial_amt`, then
   `incr_balance`).

So a connection that drops after the register goes out, or a slow reply,
leaves a funded account whose words exist nowhere. The invite is spent, so
the inviter cannot cancel it either. The person sees "the server did not
confirm registration in time", and trying again makes new words.

Fix: registration is idempotent at the mixer (`already_registered`). Keep
the profile once the register has been published, and retry.

Catch: a journey that signs up through the wire tap with the broker's
replies cut after the register. The tap needs a one-way mode for this.

### N3. A paid attachment's key can be lost

The seller's Peel answers a purchase only as a follow-up to the commit
that first stores it (`Engine.swift:820-823`, `:1055-1061`;
`answerPurchase`, `Engine+Attachments.swift:354`). If the app stops in
between, or the answer's publish fails, nothing answers later:

- there is no sweep at launch;
- a restore skips purchases on purpose.

The buyer has paid, waits for ever, and cannot buy again.

Fix: on connect, answer every paid purchase that has no answer.

Catch: the payments review's journey 4 (a paid attachment in a direct
message), still not built, with the seller's engine closed between the
purchase and the key.

### N4. History can leave permanent gaps

`syncMessages` asks for everything above the highest server index stored
(`Engine+History.swift:9-16`). The history cursor lives only in memory
(`Engine.swift:153`). Gaps follow in two ways:

- A live message stored during a catch-up raises that index. If Peel
  quits before the catch-up finishes, the next launch starts above the
  live message and never asks for the rest.
- A run that stalls for 30 seconds, or gets a page the core rejects
  entirely, ends early. The next catch-up then starts above whatever live
  message came meanwhile.

Nothing on screen says messages are missing.

Fix: store the index fetched through without a gap, and catch up from it.

Catch:
- a unit test that stores a live row above the cursor, then syncs;
- a journey that cuts the tap during a catch-up while the other side
  sends.

### N5. The words may never be written down

- The words step is a checkbox held in `@State`
  (`OnboardingView.swift:20`, `:131-156`). Nothing is stored, and nothing
  asks for a word back.
- The account is registered, and funded by the invite, before that step.
  A quit there leaves an account whose words were never confirmed.
- The words can still be read later in Account with the PIN, but nothing
  prompts anyone to.

After that, every way of losing the Keychain item loses the account:

- **Forget on the lock screen**, after a lost PIN. It asks for no proof of
  the words and shows no balance (`LockView.swift:28-33`). Audit A kept
  this by design (S21), to let someone who lost the PIN start again. This
  reopens that decision, for backup's sake.
- **A new Mac, or Migration Assistant.** The item is this-device-only.
- **A change of signing team.** The item lives in the team's access group.
  The first build signed by a team other than Tom's Personal Team cannot
  see it, and the app then opens on Welcome (`AppModel.start`,
  `profile.hasAccount`).

Fix:
- Store that the words were confirmed, and confirm by asking for three of
  them.
- Keep a reminder up while the account holds sats and the words are not
  confirmed.
- Before Forget, ask for the words or show the balance.
- Before any build is signed by another team, ship a last build under the
  old one that makes each person confirm their words.

### N6. Production's server version is unknown

- Our checkout of `sphinx-swarm` (from 2026-04-17) deploys `latest` images
  with no auto-update (`src/sphinxv2.rs`). Nothing we can read reports a
  version.
- The stack runs v0.6.29. Production may run anything up to it.
- The same September pass fixed server bugs that change what our journeys
  assume, among them:
  - paying your own server-made invoice from another device credited the
    balance (upstream `3d84568`);
  - tribe purchases were neither paid out nor refunded (stakwork/sphinx#376);
  - escrow refunds could be lost (stakwork/sphinx#378).

Fix: ask for the tag production runs and record it in `testing.md`. Then
run the journeys on a stack built at that tag as well as on master.

### N7. A tribe text that may have gone out is offered for Retry

- In `deliver`, a publish that failed part-way (`.unknown`) keeps a
  payment pending but marks any other send failed
  (`Engine+Messages.swift:308-318`).
- A tribe text carries the tribe's price yet takes the second path, so
  Retry pays and posts again.
- The 30-second Retry the payments review left for Tom's decision (F11) is
  a second road to the same place.

## Smaller, read in the code and not run

Each one needs a test before it is believed.

- **Two joins at once both pay.** `joinTribe` checks "already joined"
  before an `await` (`Engine+Tribes.swift:49-58`). The app runs one join
  at a time; the CLI and an agent would not. *Inferred.*
- **Delete contact.** `deleteContact` checks for pending payments, awaits
  two publishes, then deletes the chat's rows, including a payment
  started meanwhile. *Inferred.*
- **A delete before its message.** A delete that arrives before the
  message it deletes is never applied. *Inferred.*
- **A restore that stops early.** A history page that arrives twice during
  a restore ends the run and marks the restore done (`HistoryCursor.swift`).
  *Inferred.*
- **Writing over an existing account.**
  - When the Keychain item cannot be seen, the app opens on Welcome over a
    folder that still holds the account's database (N5).
  - Create and restore then write into that database.
  - A profile copied by Migration Assistant keeps its device ID, so two
    Macs read each other's server replies.
- **Debug text.** Errors from the core, mqtt-nio and LiveKit reach the
  person as Swift debug text (`PeelError.swift:36-39`).
- **Migrations.** The schema snapshot that catches an edited shipped
  migration stops at v17 (`MigrationTests.swift`). The later migrations
  are covered by their own backfill tests. No test opens a database
  written by a shipped build.
- **Invoices with a route hint.** `pay_invoice` takes the async path for
  any invoice with a route hint and pings the hint's node, which answers
  only if it is a Sphinx server. Never run. *Inferred.*

## What held up

Checked in the same pass and right, so it need not be read again:

- One transaction per core call, with in-memory state set only after the
  write.
- Messages deduplicated by uuid, and statuses that only move forward.
- Server replies arrive on a per-device topic.
- Child indexes are random, so two devices of one account almost never
  give two contacts the same one. Until SR-022 lands, "random" means
  derived from the seed and the time.
- No suspension between the gate and the commit in `sendPayment`, `boost`,
  `quickBoost`, `resend`, `pay`, `buyAttachment`, `makeInvite` and
  `addContact(code:)`.
